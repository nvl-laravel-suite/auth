# Upgrading to Auth Light

This is a breaking API conversion staged ahead of the coordinated major release. Current family metadata remains ^6.0 until that release. Replace every old Action/execute interface with the owning native service operation listed in [PHP API](docs/php-api.md). Pass native arrays instead of package Data and project models/results in the consumer. No old aliases or forwarding facades remain.

Move HTTP routing, controllers, validation extraction, CSRF, throttles, headers, cookies, redirects, exception presentation and OAuth Request/session acquisition into the application. Package installation no longer changes guards or password-broker configuration. Pass the guard and session explicitly for login/logout/session establishment. Credential verification alone is not login.

Use a host User subclass with optional Sanctum/Permission traits when enabling those adapters. Install selected adapter engines explicitly. Replace the old SocialIdentityProvider binding and features.social_identities.services.provider setting with a scoped SocialIdentityProviderFactory binding (or provider_factory setting). Construct a new SDK driver from the current request for every make call; see the [factory example](README.md). Keep audited SDK validation, TOTP/WebAuthn proofs, replay checks and canonical principal resolution intact.

Retired Tenancy configuration, model branches and automatic legacy-table conversion have no compatibility path. Preserve old data, drain or expire pending old proofs and queued payloads, and use reviewed native Ownership adoption before accepting scoped traffic. Native same-table ownership adoption does not copy or delete legacy tenant tables. Do not disable Ownership to escape persisted partition checks.

Keep source-transaction committed audit and delivery listeners, native queued envelopes and explicit actor/metadata contracts. Rebuild configuration/event caches and restart workers after deployment. Physical absence of optional dependencies requires a clean consumer dependency resolution; a development suite vendor directory does not prove it.

Map `users.manageCredentials` and `users.verifyEmail` explicitly in host management policies. Password edits or removal require the former; an explicit verified-email override requires the latter. An email change clears verification unless an authorized explicit override is supplied. Configure `features.password.services.policy` to replace the default new-password policy. Existing shorter credentials remain usable; bcrypt inputs over 72 bytes are always rejected. Password changes rotate native remember credentials without deleting unrelated application tokens or sessions.


## Mandatory authentication proofs

Apply `2026_10_27_000002_nvl_auth_ensure_authentication_challenges.php` under the existing migration owner. Native proof storage is mandatory even with magic links, security codes and TOTP disabled. Schema planning and Doctor require it. The forward migration intentionally repeats the frozen historical challenge definition so historical migrations remain unchanged; SchemaManager uses this same current creation/repair path. Existing business records survive, partial unsafe schemas require a data-preserving host migration, and host-owned migration mode never applies DDL automatically.

Replace removed `AuthenticationSessions::establish` / `establishForPurpose` with native proof-backed completion. Legacy/generic login links cannot be promoted; request fresh native authentication links. Email request methods now require trusted browser/guard context. Passkey begin requires context and finish returns a proof. Social browser login uses `startAuthentication` / `finishAuthentication`; existing account link management remains separate. See [method and continuation examples](docs/php-api.md#proof-backed-completion).

Enrolled MFA is mandatory across all login methods, including when TOTP is disabled. Restore an available enrolled/recovery method instead of relying on the feature flag to erase the requirement. Configure additional class-based assurance via `features.authentication.services.assurance`; consumers retain routes, requests, responses, delivery, UI and owner authorization.

Native recent authentication now authorizes sensitive self-service operations. Call `AuthReauthentication::confirm()` before starting a mutation transaction, then pass its opaque grant and the trusted `AuthenticationRequestContext` to the operation. Grants are subject/purpose/guard/session/revision-bound, expire at 300 seconds and are one-use; mutation rollback restores the grant but never the previously committed factor proof. Replace `currentPassword` mutation fields and raw `AccountConfirmation` implementations with the safe evidence/purpose policy contract. Laravel password-confirmed timestamps are presentation only. Passwordless UV passkeys are supported; linked-social reauthentication is explicitly unavailable until its receipt integration. Administrative/system authorization remains separate. See [the PHP API](docs/php-api.md#native-recent-authentication).

Browser transitions now reject an enclosing transaction on their participating native source connections with `stateful_transaction_unsupported` (409), before consuming proof or changing the guard/session. Commit registration/domain work first, then log in; self-deletion with logout must likewise start outside a host transaction. Standalone persisted proofs and stateless token operations remain transaction-aware. For a consumer composition that immediately establishes a session, call `AuthenticationSessions::assertCanTransition()` before invoking a primary verifier/SDK or pulling OAuth session state. Native finalizers also enforce the boundary. Immediate login failure clears partial browser state, invalidates the session and rotates CSRF; a failed session rotation cannot count as success. Laravel guard events can already have fired before later failure and cannot be retracted; native domain success follows its owning commit. Custom guards/session stores must honor their own logout/invalidation contracts.

## Canonical email identity and initial verification

The forward `2026_10_27_000003` migration adds the mapped, protected `email_identity_hash` column and full unique index. Fresh storage is non-null; retained rows remain unchanged with nullable keys until explicit adoption. Drain legacy workers and disable identity writes throughout adoption. Run `php artisan nvl:auth:adopt-email-identities` to inspect bounded collision references, resolve collisions explicitly, then run `php artisan nvl:auth:adopt-email-identities --apply --reason="Reviewed identity adoption" --correlation="change-reference"`. The host must authorize `nvl.auth.users.adoptEmailIdentities` through `SystemMutationAccess`. No email/password/record is normalized, merged or deleted by this adoption. Backfill commits separately before package-owned non-null DDL; MySQL DDL is not rollbackable with that data transaction. With `migrations.enabled=false`, the package fills authorized keys but does not finalize host schema: `finalized=false` until your host migration supplies the non-null constraint. Run doctor before restoring identity writes. Native email login/lookups remain unavailable while adoption schema is incomplete.

Native email identity is SHA-256 of UTF-8 lowercase(trim(email)), with no plus/dot rewriting, including soft-deleted identities. Native Eloquent models derive keys from final email attributes, including factory overrides. Query-builder/raw SQL host writes must maintain this invariant and the security revision themselves. Never accept a key from request/provider claims. Existing custom providers must supply an explicit compatible identifier/broker adapter; external Eloquent models retain their own identifier semantics and are outside native email identity guarantees.

`AuthEmailVerification::request($subject)` now emits a one-use `token` in typed delivery. Deliver it privately with `subject_type`/`subject_id`; the consumer passes it to `verify($subject, $token)`. A signed URL or cached verified model alone is no longer verification authority. Tokens bind exact current destination and revision for 60 minutes by default. Invalid, expired and replayed proofs reject even when the account is already verified; a valid unspent proof may return false after a separate valid verification. Laravel Verified and delivery run after the outer source commit.

Native signup is now explicitly admitted by the registration feature and Closed/InvitationOnly/Open mode. Existing installations creating invited principals must enable registration and choose invitation_only or open. This does not disable authenticated existing-recipient acceptance or invitation cleanup. Migrate caller-asserted social invitation registration to AuthRegistration::registerInvitedSocial using a native one-use continuation and exact recipient mailbox proof. The raw social branch is rejected before host mapping. Remove SocialSubjectResolver and AuthSocialIdentities integrations; use AuthSocialAuthentication and AuthSocialLinks. Public signup returns a principal without authenticating: commit application onboarding before browser login.


## Native account, browser and impersonation adoption

1. Run the forward principal-security and normalized-email adoption migrations before authentication traffic; review collisions without merging accounts. Run the 2026-10-28 pending-email, browser-session, remember-credential and impersonation migrations in order. With host-owned migrations, publish/review/run the same schema yourself. All participating principal, proof, audit and security stores must share the same actual connection.
2. Replace self-profile email writes with `AuthEmailChanges::request` and destination proof through `complete`. The original verified mailbox remains live until completion. Consumers route and deliver typed verification/notification events privately. Administrative identity edits retain separate management authority.
3. Enable `features.managed_sessions` only after installing per-request native admission after Laravel authentication and before application authorization. Existing sessions cannot be imported: require a fresh native verified login. Use server-side file/database/Redis storage, never the cookie session driver; configure secure cookies. Set `admission_integrated` only after the middleware is active. For managed remember-me explicitly select the `nvl-managed-session` guard driver. Legacy global recallers are unsupported and must require fresh login. Revocation uses the native registry; payload cleanup may occur later.
4. Configure `ImpersonationAccess` and enable impersonation only with managed sessions and audit. Derive browser bindings in trusted transport. Apply the temporary overlay after browser admission and before application authorization. Start/stop rotate session/CSRF/binding; never persist a target login or recaller. Native sensitive mutations stay denied during an overlay; application policy may add restrictions. Audits preserve original actor and effective subject, including deferred delivery.
5. Keep lifecycle stages continuation-based: call the original terminal exactly once, preserve identity, and return its exact result. Hooks cannot weaken mandatory security, registration, MFA, revision, owner or last-primary-method checks. Native services remain the complete operation boundary; no Fortify/Jetstream dependency or package-owned routes are introduced.
