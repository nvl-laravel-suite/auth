# Flows

Stateless password login calls `Authentication::loginWithToken()` with credential/token arrays, bounded request context and, when enrolled, TOTP or recovery proof. Native principal, token, metadata and audit writes share one transaction; host audit callbacks and facts follow its outer commit. No session or web guard is accessed. Browser `Authentication::login()` accepts credential/context arrays, StatefulGuard, Session and optional factor proof. Without enrolled proof, it retains an opaque continuation only in that server session, backed by the existing locked Challenge store for shared attempts and one-use/password/expiry binding and throws `second_factor_required`. The host redirects to its factor form; `completeSecondFactor()` consumes the same session continuation after native TOTP/recovery verification and completes canonical eligibility, pipeline, metadata, audit and session work. No consumer assembles a successful session from a bare principal ID. Changed passwords, expiry, exhausted attempts, replay, inactive/locked principals and pipeline substitution reject. Passwordless/social session establishment separately reloads and rechecks canonical principals before and after its configured pipeline. Passwordless/social consumers establish a session only after native proof succeeds. Owner intent consumption selects an owner once; membership and current availability still decide admission. Invitation acceptance/register, password reset, TOTP, recovery-code and passkey services retain their transaction and replay boundaries.

### Explicit social workflows

Use `AuthSocialAuthentication::beginLogin/completeLogin`. An unknown identity returns `registration_required` plus a redacted continuation; matching email never selects a local account. Commit signup separately and initiate a new login. Store the native intent and its trusted context in the server session; the SDK independently validates OAuth state. Use `AuthSocialLinks::beginLink/completeLink` or `beginReconnect/completeReconnect`: recent proof is consumed before redirect, and callback authority comes from the original one-use intent. Reauthentication requires the same active linked provider subject and still applies native MFA. SDK work runs outside source transactions; restart authorization if an external code was spent before a local failure. The overloaded `completeAuthorization` path is retired.

Social signup consumes `AuthRegistration::registerSocial` continuations for Open mode. InvitationOnly uses `AuthInvitations::registerSocial` with the actual invitation token and exact proved recipient. No API accepts raw provider IDs or verification flags. Missing provider email requires `requestSocialEmailVerification` and `verifySocialEmail`; delivery uses `RegistrationEmailVerification`, with five code attempts, five mailbox requests and the original 300-second continuation deadline. The replacement receipt revokes its predecessor. Local mailbox proof is stored separately from provider provenance. Signup never emits login authority; start a fresh login after the outer commit.

### Pending email replacement

Call `AuthEmailChanges::request` with an EmailChange recent grant. The old verified email remains the live login identity. Deliver `EmailChangeVerification` tokens privately to the replacement address; deliver `EmailChangeNotification` facts to the old address. `complete` consumes the destination/browser/revision-bound token once within 60 minutes, rechecks global uniqueness and advances security revision. Completion never authenticates. A newer request supersedes the old pending row. `cancel` only revokes that subject's pending request. Consumers supply host routes, neutral errors, no-store/referrer controls and notification delivery. Generic profile updates reject immediate identity replacement; administrative email edits retain their separate abilities.
